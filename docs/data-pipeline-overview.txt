HKS COURSE EXPLORER DATA PIPELINE

Historical evaluations:
  data/canonical_courses_enriched.csv
  data/historical_parity_registry.json
    -> scripts/build_data.py
    -> public/courses.json and public/sim_coords.json
    -> reviewed Supabase migration for one same-ID evaluation enrichment and
       canonical-only observations
    -> Supabase courses (course cards, comparisons, faculty, evaluation graphs)
    -> public/sim_coords.json (content-similarity coordinates only)

The parity registry is a versioned reconciliation manifest, not a second set of
ratings. It retains an existing database ID only for a unique observation with
the same course/professor/term identity, aggregate provenance, respondent count,
ratings, and evaluation/bidding state. It separately preserves every database-
only observation and every genuinely distinct canonical observation. It never
deletes, rekeys, or transfers ratings between observations.

Current offerings:
  my.harvard
    -> scripts/sync_myharvard_hks.py
    -> stage, count-verify, and atomically promote authoritative HKS rows
  Harvard ATS API (non-HKS schools only)
    -> scripts/sync_live_courses.py
    -> service-only atomic Supabase RPC
    -> Supabase live_courses
    -> Browser Schedule Builder, scoped to the selected term

The browser never searches my.harvard or the Harvard ATS API directly. Both
are trusted daily-ingestion sources only. HKS and non-HKS source ownership is
disjoint. Student searches and browsing use the last successfully synced
`live_courses` data, so a temporary upstream failure cannot make an otherwise
healthy browser search depend on either provider.

Section meeting data:
  Harvard source/section import process
    -> Supabase course_sections
    -> Browser Schedule Builder meeting-time enrichment

Safety rules:
- The canonical CSV is reviewed input; build validation rejects fatal data errors.
- Generated duplicate course IDs fail the trusted loader before a database
  client is created; last-write-wins is not an accepted promotion behavior.
- Any failed source request aborts a live-sync run before upsert or stale deletion.
- The general ATS sync excludes HKS; only a count-verified my.harvard run may
  change the active HKS catalogue.
- Harvard result pages use the documented scroll cursor. Any malformed, repeated,
  or failed page aborts the entire run before data can change.
- A complete validated source payload is upserted in one database transaction;
  a database error leaves the previously served live catalogue intact.
- The future private `catalogue_snapshot_v1` contract remains disabled until
  historical-source parity and rollback evidence have been accepted. It must
  not replace the current browser reads early or infer evaluation history.
